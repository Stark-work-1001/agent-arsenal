# 05 · 经验文档

> 只记录**踩过并已解决**的坑，以及同类项目可复用的判断。

## 一、SQLite / 检索

### 1. `node:sqlite` 的 FTS5 索引列不等于表列

建虚表时写了 `content='search_docs'`，外部内容表模式下虚表只暴露**索引列**（name/summary/body/keywords/author/hosts），
`capability_id` 这类非索引列必须 JOIN 主表拿：

```sql
SELECT d.capability_id, bm25(search_fts) AS score
FROM search_fts JOIN search_docs d ON d.rowid = search_fts.rowid
WHERE search_fts MATCH ? ORDER BY score
```

直接 `SELECT capability_id FROM search_fts` 会报 `no such column`。

### 2. unicode61 不切中文，trigram 也不切

实测：

| 方案 | 查询「能力中枢」 |
| --- | --- |
| 原样写入 + unicode61 | 空 |
| 原样写入 + trigram | 空 |
| CJK 逐字空格后 + unicode61 | 命中 |
| trigram 且查询为 ASCII | 命中 |

结论：**入库与查询两侧都做 CJK 逐字切分**，是零依赖下最稳的路径。
代价是「能力」和「力能」在索引层面等价，因此排序时用应用层字符对覆盖率补正。

### 3. `bm25()` 返回负值

FTS5 的 `bm25()` 越小越相关（负值）。直接当分数用会排反，取相反数即可。

## 二、Electron

### 4. 开发环境中的全局 `ELECTRON_RUN_AS_NODE=1`

这个变量会让 `electron.exe` 以 Node 模式运行，于是 `require('electron').app` 是 undefined，
报 `Cannot read properties of undefined (reading 'disableHardwareAcceleration')`。

对策：所有启动脚本 `delete env.ELECTRON_RUN_AS_NODE` / `env -u ELECTRON_RUN_AS_NODE`；
打包启动器里 `set ELECTRON_RUN_AS_NODE=` 清空。

### 5. preload 默认按 CJS 加载

把 preload 写成 `import { contextBridge } from 'electron'`（ESM），会静默失败：
页面加载了，但 `window.arsenal` 是 undefined，界面一片空白。
即使 package.json 有 `"type": "module"`，preload 仍按 CommonJS 处理——**必须用 `require`**。

### 6. 打包后路径要按 exe 位置推

`__dirname` 在 asar/打包环境与开发环境不同，资源路径用 `path.join(here, '..', '..', 'dist-renderer')` 这种相对推导，
比写死绝对路径稳；数据目录同理（`runtime/` 下要上移一级）。

### 7. 截图验收比肉眼点更快

给主进程加一个 `ARSENAL_SHOT` 环境变量通道：启动后 `executeJavaScript('__arsenalGoto("view")')` + `capturePage()`，
一次启动就能拿到全部视图的真实渲染结果。配合 `ARSENAL_SHOT_WAIT` 等首扫完成，避免截到空库。

## 三、设计陷阱

### 8. 「已剥离 frontmatter 的正文」不能用来判断有没有 frontmatter

最初规则是 `!/^---\n/.test(inst.content)`。但 `inst.content` 存的是适配器解析后的**正文**，
frontmatter 早被剥离——于是 259 个正常技能全被判成「缺 frontmatter」。

正确做法：**在解析时记录事实**（`metadata.hasFrontmatter`），诊断只读事实。
这条经验可以推广：*不要让下游用不完整的数据反推上游状态*。

### 9. 安装路径是目录还是文件，必须显式解析

技能/插件的 `installations.path` 是**目录**，MCP 配置项是 `文件#name`。
任何「写文件」的修复动作都要先 `resolveEntryFile()`，否则会尝试把目录当文件 rename，报 EPERM。

### 10. 跨盘 rename 会失败，且必须显式暴露

`fs.renameSync` 在跨卷时抛 `EXDEV`（Windows 上可能是 EPERM）。
删除到回收站（可能在另一个盘）后再恢复，就会静默失败。
对策：捕获后退化为 `copy + remove`，并把 `errors` 一起返回给界面——**不要吞掉失败**。

### 11. 串行打 npm registry 是不可行的

313 个能力逐个 `npm view`，实测 4 分钟仍未完成。
结论：**本地缓存优先**（3057 条 DSH Market 条目，43 ms 全量比对），联网只作可选补充，
并发上限 6、TTL 6 小时。

### 12. 组合根改组服务时，旧引用会静默失效

`createContext` 从 `ctx.registry` 改成 `ctx.services.registry` 后，
`scanner.js` 里残留的 `this.ctx.registry` 变成 undefined，扫描全部来源失败但错误被 per-source catch 吞掉，
只在日志里留一行。对策：**保留别名 + 在组合根显式赋值**，并且扫描错误要进事件流（已做）。

## 四、数据模型经验

### 13. 「逻辑能力 / 物理实例」是跨宿主管理的必要条件

同一技能在 6 个宿主下各一份，如果平铺成 6 条记录：
检索结果被淹没、去重无法表达、版本比较没有对象。
拆成两层后：身份键唯一确定逻辑能力，安装实例承载路径/指纹/正文，去重变成「同一逻辑能力的多实例」或「相似逻辑能力」。

### 14. 身份键用「作者/名称」而不是路径

路径会变（重装、迁移、不同宿主目录），作者+名称稳定。
没有作者时退化为名称，但要允许后续补全（`author_source` 字段记录来源）。

## 五、提升建议（如果继续做）

1. **语义检索**：当前 300+ 能力用 BM25 足够；到 3000+ 时应引入本地 embedding（如 bge-small-zh），按「向量召回 + FTS 精排」融合。
2. **依赖预检**：现在是静态判断（文件是否存在），可升级为「沙箱子进程探活」——启动 MCP server 发 `initialize`，超时即判故障。
3. **能力执行代理**：目前只做「检索 + 读取」，可以加一个受控执行层，把 MCP 工具调用通过中枢转发并记录耗时/错误率。
4. **增量扫描**：现在是全量（23 s），可以按 mtime + 目录指纹做增量，降到 1–2 s。
5. **多工作区**：把「项目级」能力（`.claude/skills` 之类）纳入来源，按项目维度过滤。
6. **协作维修**：派单目前是生成工单文本，可以接 A2A 直接把工单推给另一个智能体并跟踪状态。
