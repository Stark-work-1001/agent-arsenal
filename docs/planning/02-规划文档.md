# 02 · 规划文档

## 1. 产品定位

**Agent Arsenal（智能体核武库）** 是一个 Windows 桌面应用形态的**跨智能体能力中枢**：

- 采集：把本地所有智能体生态里的能力（技能 / MCP / 插件 / 提示词 / 智能体定义）统一扫描入库
- 中枢：以 SQLite 为单一事实源，提供检索、详情、状态、健康、版本、来源
- 分发：通过 MCP 协议让任何智能体主动检索与读取；通过生态同步把端点写进宿主配置
- 治理：去重裁决、故障诊断、维修派单、更新巡检、生命周期与回收站

**明确不做**：不代替宿主执行技能；不自动改宿主代码；不做云同步与账号体系。

## 2. 技术选型与理由

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 桌面壳 | Electron 44 | 可复用本地已有的运行时缓存；主进程即后端，无需 sidecar；调试与截图验证成本低 |
| 界面 | React 19 + TypeScript + Vite 7 | 组件化、构建快；打包后 309 KB JS（gzip 91 KB） |
| 数据库 | SQLite 3.51（`node:sqlite` 内置） | 零编译依赖；FTS5 + trigram + JSON1 全部可用 |
| 后端 | Node 24 ESM | 与 Electron 同进程，IPC 直接调用，无跨进程序列化开销 |
| 对外协议 | MCP（stdio + Streamable HTTP） | 事实标准，主流智能体均支持 |
| 检索 | FTS5 BM25 + trigram + 结构化 + 同义词 | 离线、可解释、零模型依赖 |
| 打包 | 绿色目录（Electron 运行时 + 应用 + 数据） | 开发自用阶段，不做安装包与签名 |

## 4. 数据模型

| 表 | 职责 |
| --- | --- |
| `sources` | 扫描来源（路径 + 类型 + 宿主 + 上次扫描状态） |
| `capabilities` | **逻辑能力**：身份键唯一，含作者/版本/状态/健康/使用计数 |
| `installations` | **物理实例**：一份能力在某个路径下的副本，含指纹、正文、清单快照 |
| `search_docs` + `search_fts` + `search_trigram` | 检索索引（触发器同步） |
| `duplicate_groups` | 重复候选组与裁决结果 |
| `faults` / `repairs` | 故障工单与维修历史（含修复前后哈希） |
| `backup_snapshots` | 文件/目录/数据库备份，可回滚 |
| `updates` / `registry_catalog` | 版本检查结果与上游目录 |
| `agents` / `agent_sessions` / `heartbeat_files` | 智能体识别与会话 |
| `workflows` / `workflow_runs` | 工作流定义与执行记录 |
| `events` / `capability_usage` / `settings` / `meta` | 审计、用量、设置、元信息 |

**双轨存储**：元数据在 SQLite；纳管的能力实体在 `arsenal/{skill,mcp,plugin,prompt}/` 分散目录。
这是刻意的——能力包本身是文件（有脚本、资源、README），塞进数据库反而失去可移植性。

## 6. 关键设计决策

1. **逻辑能力与物理实例分离**：没有这层，跨 6 个宿主的同名技能会变成 6 条互相竞争的搜索结果。
2. **CJK 逐字切分**：不引入外部分词器，索引与查询两侧同构。
3. **诊断只读元数据**：故障规则不重新读文件内容（那样会把「已剥离 frontmatter 的正文」误判为缺 frontmatter，实测导致 259 个误报）。
4. **修复入口解析**：安装路径可能是目录，修复必须落到目录内的 `SKILL.md`。
5. **删除 = 移入回收站**：`.trash` 目录 + `archive_path` 记录，跨盘时退化为复制后删除。
6. **更新检查缓存优先**：3057 条本地目录先导入，联网只作补充。
